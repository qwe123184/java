# 变更说明 · 2026-11-16

## 现象

运行 `start-all.bat` 后状态为：Frontend 5173 = YES、MySQL 3306 = YES、**Backend 8081 = NO**。

## 根因

**1）真正的失败点：Maven 编译失败，jar 没生成**

`GameService` 接口里新增了 `GameStatVO getGameStat(Long userId)`（供 `/api/me/overview` 个人中心总览使用），但 `GameServiceImpl` 没有实现它：

```
[ERROR] GameServiceImpl 不是抽象的，并且未覆盖 GameService 中的
        抽象方法 getGameStat(java.lang.Long)
[INFO] BUILD FAILURE
```

于是 `target/springBootTest-0.0.1-SNAPSHOT.jar` 不存在 → `start-backend.bat` 无 jar 可跑 → 8081 不会监听。前端和 MySQL 与后端相互独立，所以它们仍是 YES。

**2）隐藏坑：环境变量覆盖 server.port**

部分开发终端（WorkBuddy / IDE 内置终端）会注入 `SERVER__PORT=52888`、`SERVER__HOST=127.0.0.1`。Spring Boot 的松绑定会把 `SERVER__PORT` 当成 `server.port`，覆盖 `application-dev.properties` 里的 8081；直接手动 `java -jar` 会报：

```
Web server failed to start. Port 52888 was already in use.
```

`start-backend.bat` 原本已清理 `SERVER__PORT / SERVER__HOST / SERVER_PORT`，本次再给 java 启动命令加 `-Dserver.port=8081`（Java 系统属性优先级高于环境变量）做双保险。

## 改动文件

| 文件 | 改动 |
| --- | --- |
| `springBootTest/src/main/java/com/fenglin/springboottest/service/impl/GameServiceImpl.java` | 新增 `getGameStat(Long)`：只读查询 `zhan_shen.t_user_game_stat`，无记录或字段为 null 时返回全 0 的 `GameStatVO`；新增私有 `nz(Integer)` 做空值保护。只读不写库，避免在个人中心查询接口里产生副作用。 |
| `start-backend.bat` | java 启动行加入 `-Dserver.port=8081`（字节级替换，保留原有 GBK 编码与 CRLF 换行）。 |

## 下次开机怎么启动

1. 若 8081 / 5173 都没有监听：直接双击 `start-all.bat`。代码已修复，脚本会重新构建并依次拉起后端、前端。
2. 若端口已被占用（本次是用后台进程方式启动，没有可见控制台窗口）：可先运行 `stop-all.bat`，再运行 `start-all.bat`；直接运行 `start-all.bat` 也可以，脚本检测到端口已监听会跳过并打印全 YES 状态。
3. 后端再次起不来时，先看 `springBootTest/log/` 下的日志；若 jar 不存在，在 `springBootTest` 目录手动执行 `mvn package -DskipTests`，编译报错会直接显示。

## 追加修复：试炼「答完没有显示结果」（2026-11-16 09:12）

**现象**：境界突破第 3/3 题选完 D 后，页面停在题目上，不出现「突破成功 / 突破未竟」结果页。

**排查结论（后端无问题）**
- `springBootTest/log/backend-run.out.log` 中没有任何 `/game/stage/submit` 的痕迹：既没有逐题 `SELECT ... t_quiz WHERE id=?`，也没有 `UPDATE zhan_shen.t_user_stage`，更没有 ERROR 堆栈 —— 说明提交请求根本没发出。
- `zhanshen/src/components/game/RealmTrial.vue` 的 `choose()` 只把选项写进 `picked`，最后一题既不跳题也不提交；必须再点选项**下方**的「提交试炼」按钮，而该按钮正好在截图可视区之外，答完容易以为「没反应」。
- 另一个隐患：`submit()` 的 catch 读的是 `e.response.data.message`，但后端 `Result` / `GlobalExceptionHandler` 统一返回字段是 `msg`，所以真失败时只会闪一句「提交失败」，看不到真实原因。

**改动**：`zhanshen/src/components/game/RealmTrial.vue`（保留原 CRLF 换行）
- 最后一题选完后约 0.9 秒自动提交；期间点题号回去改答案会取消自动提交，改由「提交试炼」按钮手动提交（保留用户检查答案的机会）。
- 新增 `errMsg()` 兼容 `msg` / `message`；失败原因常驻显示在按钮上方（`.submit-error`），不再只靠 2.4 秒的 toast；按钮在请求期间显示「提交中…」。
- `submit()` 增加防重入；重新开启试炼时清空错误提示与定时器。

**验证**
- 用已有账号经 5173 代理实测：`POST /game/stage/start` → 3 题、阈值 2；`POST /game/stage/submit` → `code=0`、`passed=false`、`correctCount=0/3`、`review` 3 条且含 `correctAnswer`（结果页所需数据齐备）。
- 刻意使用全错答案，避免推进境界：`t_user_stage` 的 `current_realm / max_realm / clears / exp / best_streak` 提交前后完全一致。
- Vite HMR 已重新编译该组件，日志无语法错误。

**注意**：热更新会重置组件状态，当前正在答的那一局会回到「境界之路」。刷新页面、重新开启试炼，答完最后一题即可看到自动出结果。
